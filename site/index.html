// WHY QA

Testers already think in failure modes

A lot of SRE comes down to two questions: what happens when this breaks, and how would we know? That's a tester's whole job. These are the habits I brought over from QA, and where you can see them in the projects above.

Red has to mean broken

A flaky test teaches people to hit re-run. A noisy alert teaches them to mute the channel. Same problem, different layer. I'd rather stay quiet or skip honestly than fail for the wrong reason.

  • OT: a curtailed park sends nothing
  • Take-home: skip on Cloudflare, don't fail
  • Lab: pending windows and a Watchdog

Assume the other end is unreliable

Live systems lag, hang and half-answer. So I poll for the state I need instead of sleeping, put a timeout on every call, and treat "no answer" as its own state, never as zero.

  • OT: silence is never 0 MW
  • Take-home: poll, don't sleep
  • Platform: post-deploy health check

Test what ships, not just the code

Outages rarely come from the function with full coverage. They come from a security group, a network path nobody checked, an install step that only works online. So those get tests too, and they run before production.

  • OT: every network path tested
  • Platform: tfsec before plan, gated apply
  • Lab: offline install rehearsed in CI

Check the real thing, then clean up

A pass from last week says nothing about a live system today, and test data left lying around breaks the next run. Check what's actually there, own your data, and leave things the way you found them.

  • Take-home: own ids, tests clean up
  • Platform: drift reports
  • Platform: throwaway kind cluster
