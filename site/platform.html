Cloud-native deployment platform

// 01 · PROBLEM

Ship a small API and a background worker to AWS the way a production team would, not the way a tutorial does: a private network, secrets that never touch the repo, no long-lived cloud keys in CI, and nothing reaching production without tests, a security scan and a human approval. Then notice when someone changes it by hand.

  • No keys in CIShort-lived credentials through OIDC, issued per run.
  • Gated changesTests and scans first, apply only after approval, rollback by commit SHA.
  • Drift is visibleA scheduled report of anything changed outside Terraform.

// 03 · KEY DECISIONS

Choices that shape every deploy

OIDC, not stored keys

GitHub Actions assumes an IAM role for each run, so there's nothing in the repo or its settings to leak and reuse. A separate least-privilege role covers the incident log workflow. See terraform-apply.yml and the trust policy.

Plan, apply and destroy are separate

Plan is for review. Apply needs a typed confirmation and approval in the production environment. Destroy is manual only, because it's the riskiest thing the repo can do.

Deploy what CI built

Every Terraform workflow takes its image tags from the latest successful CI run on main, so nothing reaches AWS that didn't pass the tests and the image health check.

Rollback is just an apply

No special rollback machinery: run Terraform Apply with the SHA of a commit that worked. It's the same path as every deploy, so it gets exercised all the time.

Private tasks, private endpoints

API, worker and database sit in private subnets. VPC endpoints for ECR, CloudWatch Logs and S3 keep that traffic off the internet.

One app, two targets

The images that run on Fargate also ship as a Helm chart with a migration Job, tested in a throwaway kind cluster, so the app isn't tied to one platform.

// 04 · FAILURE SCENARIOS · DRIFT

Catching changes made by hand

Someone fixes something in the AWS console at 2am and never tells Terraform. A scheduled job runs a JSON plan with detailed exit codes, filters the noise and reports what drifted.

  • Drift report runs weekday mornings and on demand, written to the job summary and kept as an artifact.
  • Incident log pull fetches CloudWatch Logs for a time window and sorts events into ERROR, WARN, INFO and UNKNOWN, through a least-privilege OIDC role.
  • Post-deploy health check looks at the ALB, /health, ECS capacity, stopped-task reasons and recent errors.

// 06 · TRADE-OFFS

Decisions I'd defend, and what they cost

Fargate behind an ALB

More AWS than a small API needs. In return: private tasks, a single public entry point, health checks, rolling deploys and clear IAM boundaries.

RDS and Secrets Manager

Heavier and pricier than a Postgres container. Worth it to make persistence, its failure modes and who owns them explicit.

OIDC instead of keys

Safer than stored AWS keys, but a broken trust policy can look exactly like a broken deploy. Knowing that is half the debugging.

Separate plan, apply, destroy

Limits the blast radius. Apply needs a confirmation and an approval, destroy is manual only, and rollback is an apply with a known-good image SHA.

// 07 · LESSONS LEARNED

What I'd tell myself at the start

  • A broken trust policy looks exactly like a broken deploy

    With OIDC, a mistake in the IAM trust policy shows up as a deploy that fails before Terraform even runs. Checking the identity step first saves a lot of time spent staring at the wrong logs.

  • Separate workflows are cheap insurance

    Splitting plan, apply and destroy cost a few extra YAML files. In exchange, the riskiest action can't run by accident, and every apply has a person's approval on it.

  • A drift report is only useful once it's quiet

    A raw plan is too noisy to read every morning. Filtering it down to creates, updates, replacements and deletes is what turned it into something worth reading.

  • Production shape costs real money

    Fargate, a load balancer and RDS are more than a small API needs, and they bill by the hour. The AWS path earns its place by showing real boundaries, as long as destroy works as well as apply.
