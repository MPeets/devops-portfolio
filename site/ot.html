PROJECT 01 · FLAGSHIP

OT energy monitoring

// 01 · PROBLEM

A generation fleet sits behind OT network boundaries: wind turbines, solar inverters, a battery, and the substation that connects them to the grid. Monitoring has to read through those boundaries without opening a way in, and it has to be right at 3am. Plenty of dashboards show a silent turbine as 0 MW and a curtailed one as a fault, and both send someone out for the wrong reason. I've worked that night shift for real, as the person answering alarms from 200+ remote pumping stations, so I know what a misleading alarm costs.

  • Never mistake no data for no outputSilence is a state of its own, not 0 MW, and it mutes everything built on the missing data.
  • Judge output against physicsAgainst what the wind, the sun and the setpoints allow. Curtailment is never a loss.
  • Read OT, never write to itOne read-only path in, proven from inside every network.
  • One cause, one pageA dead link or a grid trip arrives as one notification, not a flood.

A lab, not a plant. The devices and their physics are simulated in containers and generic: they don't model any real site and haven't been run against real equipment. The monitoring stack, its configuration and its tests are real. Section 06 spells out what's validated and what isn't.

// 02 · ARCHITECTURE

Four networks, and data only moves one way

Field on the left, control room on the right. Data moves up from the devices to the people watching them, and each network only reaches its neighbour. The gateway, the collector and Prometheus each sit on two networks and route nothing between them.

The only way into OT. Routes each request by Modbus unit id from the inventory, and answers anything but a read with exception 1, Illegal Function. A unit id that isn't in the inventory gets nothing: nothing scans for devices.

One panel stacks what the weather allows, what the setpoints allow and what the fleet makes, so curtailment and lost energy show up as separate bands. Colours follow cause:

  • low wind or standby
  • fault

What can reach what, and how it's proven

Each network is checked from the inside. scripts/check-segmentation.sh starts a throwaway container on each network and tries every path. Blocked paths are tried by name and by every IP address the target has, since a name that doesn't resolve proves nothing on its own. CI runs it on every push, and again on the copy installed from the offline bundle.

// 03 · KEY DECISIONS

The decisions that make it credible

Installing Prometheus is the easy part. These are the calls that decide whether anyone trusts what it says.

No data is never no output

Whether a device answers comes from the collector's per-device gather counter, which exists whether the device answers or not. No comms alert looks at power, no generation alert fires for a silent device, and silence is purple on every dashboard.

Judged against physics

A turbine against its power curve at its own wind, an inverter against its irradiance, both capped at their power limit. Calm nights, curtailment and clipping lower the expectation instead of counting as losses. A contract test keeps the simulator, rules and dashboards on one curve.

Real grid thresholds

The Baltic grids have run synchronously with Continental Europe since February 2025, so frequency alerts use that area's System Operation Guideline criteria. They work from the median of at least three meters, so one bad meter gets its own alert and pages nobody.

Cause before number

Protection trips at its limit either way. The transformer alert compares oil temperature with what its load explains, so failed fans show up around 55 °C, long before an 85 °C alarm. The battery alert watches cells still climbing while charging.

One cause, one page

No data mutes everything that depends on it, resolved notifications included. Critical mutes its own warning. A grid voltage alert mutes the trip it caused, and stays on through the unit's 60 second reconnect.

IT can't generate traffic into OT

The collector polls on its own fixed schedule. Prometheus only scrapes the collector, so nothing on the IT side chooses what gets polled or how often. That's why there's no blackbox-style exporter that takes its target as a parameter.

The inventory is the asset list

A device in inventory.toml that doesn't answer is an incident. One that isn't in it doesn't exist, because nothing scans for devices. The collector config is generated from the inventory, and a test fails if it drifts.

Offline and hardened by default

Every image pinned, installed from one verified bundle with registry pulls disabled. Read-only root filesystems, no Linux capabilities, non-root processes, and only the three UIs published, on localhost.

// 06 · TRADE-OFFS

What's simulated, what's proven, what would change

The lab keeps every step small and visible. A real site is built differently, and some things would never be done the way the lab does them. From the lab to real plants goes into detail.

Simulated

  • The devices and their physics: wind field, irradiance, battery, transformer heat
  • Grid events and faults, injected from scenario files
  • The networks: Docker networks on one host, not firewalls and VLANs
  • Modbus TCP on every device

Proven in the lab, every push

  • Every allowed and blocked path, from inside each network
  • The gateway refusing writes
  • Every alert rule, including the cases where it must stay quiet
  • Routing and inhibition on a real Alertmanager
  • A device fault through to its notification and back
  • The offline install, with the registries blocked

Not validated, needs real equipment

  • Vendor register maps, agreed polling rates and timing
  • IEC 60870-5-104 or IEC 61850 station gateways and historians
  • Physical firewalls, VLANs and data diodes
  • Scale, latency, and a clustered Alertmanager
  • Change control and maintenance windows on a live site

// 07 · LESSONS LEARNED

What I'd tell myself at commit one

  • Going blind looks exactly like an all-clear

    When a device stops answering, every alert built on its data resolves, because the series are gone, not because anything got better. The no-data alerts have to mute their dependents' resolved notifications too, or the shift gets a wave of false all-clears at the worst possible moment.

  • The rule tests that matter most say "don't fire"

    67 of the 98 rule test cases check that an alert stays quiet: a calm night, a curtailed park, dusk, a storm stop, one bad meter. Firing is easy to get right. Staying quiet when it should is what earns an alert people's trust.

  • One meter is an opinion

    Frequency is the same across the whole synchronous area, so one meter disagreeing is a meter problem. Taking the median of at least three turns what would have been a page into a warning for the shift.

  • Monitoring shouldn't choose what it polls

    An exporter that takes its target as a scrape parameter would let the IT side generate traffic into OT. A collector in the DMZ with a fixed schedule takes that choice away, and the scrape config never names a device.

  • Image IDs aren't portable

    Docker's classic and containerd image stores give the same image different IDs, so a bundle built on Docker Desktop would fail its check on a Linux server. Verifying platform and filesystem layers instead makes the offline install work on both.
