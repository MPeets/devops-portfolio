PROJECT 04

Test automation take-home

// 01 · PROBLEM

Luminor's take-home for a QA automation role: API sanity checks for the public Petstore and one UI journey on luminor.lv, in a fixed Java stack. Both are live systems I don't control, a shared sandbox that lags and hangs and a bank's website behind Cloudflare. Writing the tests was the easy part. Making them tell the truth was the work.

  • Fail for a real reasonNever because of timing, shared data or a blocked runner.
  • Leave no messEvery test owns its data and cleans up after itself.
  • Repeatable anywhereSame result on a laptop and a fresh CI runner.
  • Readable by a reviewerEvery quirk explained in the README and the commit history.

// 02 · ARCHITECTURE

How the suite is put together

Two suites in one Gradle project, split by JUnit tag. Each layer has one job, so a quirk of the live system gets handled in exactly one place.

// 03 · KEY DECISIONS

The live systems disagreed with the brief

Every one of these broke a test at some point. Each card is what I expected, what actually happened, and what the suite does about it now.

8 of 8

  • Writes aren't readable right away

    API
    Expected
    Create a pet, read it straight back.
    Observed
    POST returns 200 and the next GET can still 404. After a DELETE, GET can still return the pet for a moment.
    So the suite
    Polls every 250ms, for up to 10s, until the pet is readable or gone. No fixed sleeps.

  • It's a shared sandbox

    API
    Expected
    My test data is mine.
    Observed
    Everyone writes to the same Petstore. Ids the server picks collide with other people's pets.
    So the suite
    Generates large ids client-side, tracks what each test made and deletes it afterwards. That's also why the tests can run in parallel.

  • Create returns 200, not 201

    API
    Expected
    201 Created, by REST convention.
    Observed
    The live API answers 200.
    So the suite
    Asserts what the system actually does, and the README says why.

  • Sometimes it just hangs

    API
    Expected
    Every request gets an answer.
    Observed
    A connection to the sandbox can sit there indefinitely.
    So the suite
    Times out connect, socket and pool after 10s. A hung Petstore fails one test instead of hanging the whole build.

  • Errors leak implementation details

    API
    Expected
    A clean 404 for a non-numeric id.
    Observed
    It is a 404, but the body names a Java NumberFormatException.
    So the suite
    Asserts the 404 and deliberately doesn't pin the message. A leak is a bug to report, not a contract to lock in.

  • Two of every menu

    UI
    Expected
    One "Site menu" button on the page.
    Observed
    Desktop and mobile menus are both in the DOM. The first match is often the hidden one.
    So the suite
    Finds controls by role and visible name, and always takes the visible one. No CSS classes.

  • "Open" isn't open yet

    UI
    Expected
    The 2026 reports section is open on load.
    Observed
    It starts with aria-expanded=false and flips to true a beat later.
    So the suite
    Waits for the attribute to become true instead of reading it once. Load timing isn't a bug.

  • CI can't see the site

    CI
    Expected
    A GitHub runner can open luminor.lv.
    Observed
    Runners get a Cloudflare challenge instead of the page.
    So the suite
    Detects Cloudflare's own markup and aborts as skipped. Red is reserved for "the site is broken".
// 03 · KEY DECISIONS · UI LOCATORS

Six steps, and the locator behind each

Home, site menu, About Us, Financial reports, then check the 2026 section is open with a PDF in it. Every locator goes through roles and visible text, the way a person or a screen reader finds things.

STEP 1 OF 6

Open the site, or say why not

Ready means the cookie banner or the site menu exists. If Cloudflare's challenge markup is there instead, the test aborts as skipped with a note to run it locally. It checks markup, not English text, so a Latvian or Russian challenge page counts too.

Selenide.open("https://luminor.lv/en");
Wait().withTimeout(Duration.ofSeconds(15))
    .until(driver -> siteReady() && !cloudflareChallenge());
STEP 2 OF 6

Accept cookies if they ask

The button looks all caps, but that's CSS. The accessible name might not be, so the match ignores case. CI is a fresh browser every time, so the banner shows up there more often than locally.

$(byRole("button", "ACCEPT ALL",
    fullText().caseInsensitive()))
STEP 3 OF 6

Open the site menu

Desktop and mobile versions of the menu are both in the DOM. Taking the first match clicks something invisible half the time, so it takes the visible one.

$$(byRole("button", "Site menu")).find(visible)
STEP 4 OF 6

About Us

After each click it waits until aria-expanded says true or the next control is visible, whichever comes first. Sometimes the panel shows up before the attribute does.

$$(byRole("button", "About Us")).find(visible)
STEP 5 OF 6

Financial reports

The page counts as loaded when its heading is visible, not when the URL changes.

$$(byRole("link", "Financial Reports")).find(visible)
$(byRole("heading", "Financial reports")).shouldBe(visible)
STEP 6 OF 6

The 2026 section is open, with a PDF

Wait for aria-expanded to turn true, then look for links inside that year's panel only, not the whole page. A link existing isn't enough; the href has to look like a PDF.

title.shouldHave(attribute("aria-expanded", "true"));
panel.$$(byRole("link"))
    .filter(attributeMatching("href", ".*\\.pdf(\\?.*)?"))
    .shouldHave(sizeGreaterThan(0));
// 04 · FAILURE SCENARIOS

Why the suite polls instead of sleeping

A fixed sleep is a guess. Too short and the test fails for nothing. Too long and every run pays for the worst case. Polling waits exactly as long as it has to. Run the same 30 creates both ways and compare. The lag is simulated; the poll settings are the suite's real ones.

Fixed sleep, 500ms 0 of 30 failed · 0s waiting · 0 GETs
Poll every 250ms, up to 10s 0 of 30 failed · 0s waiting · 0 GETs
passed: bar is time spent waiting failed: GET still 404 when the pet actually became readable scale 0 to 2s, same for both

Press Run to compare.

// 04 · FAILURE SCENARIOS · CI

Red means the site is broken. Nothing else.

The API suite runs on every push. The UI suite is a manual run, because GitHub's runners get a Cloudflare challenge on luminor.lv. Rather than fight it or let it go red, the test tells the three situations apart.

PASSED

The site works

The journey completes and the 2026 report PDF is there.

FAILED

The site is broken

A step times out or the PDF is missing. This is the only case that goes red, so red always gets looked at.

SKIPPED

Cloudflare blocked the runner

The result says nothing about the site, so it doesn't pretend to. The skip message says to run it locally.

  • Both suites with --continue on the manual run, so an API failure still produces a UI result and a report.
  • Allure as one HTML file. The usual folder of JSON just sits on "Loading..." when downloaded from Actions. The upload step fails the job if no report was made.
  • Test tasks are never up to date. Gradle skips tasks when nothing changed locally, but the other end is live, so last time's pass means nothing.
  • Old results get wiped before every run, so a stale result can't sneak into a new report.
// 06 · TRADE-OFFS

What I chose, and what it costs

Real systems, real flakiness

Testing against the live Petstore and luminor.lv catches what a mock never would, but a sandbox outage can still turn a run red. Polling, timeouts and cleanup shrink that risk; they don't remove it.

The UI suite is manual in CI

GitHub's runners get a Cloudflare challenge. I chose an honest skip and a local run over trying to get past bot protection on a bank's website.

Assert what it does, not the spec

The suite pins live behaviour, like 200 on create. If Petstore ever moves to 201, a test goes red. That's the right signal, but it needs a person to judge it.

Pinned report tooling

Allure is pinned to 2.34.1 because Allure 3 showed an empty report with the results sitting right there. Stable today, and one more thing to revisit later.

// 07 · LESSONS LEARNED

Same instincts, one layer down

None of this is specific to a pet store. Every decision above has a direct twin in running infrastructure.

  • In this test suiteIn infrastructure
  • Poll until the pet is readable, never a fixed sleep Readiness probes and post-deploy health checks instead of sleep 30 && curl
  • A 10s timeout on every HTTP call Timeouts on jobs and probes, so a hang turns into a clear failure
  • Skip on a Cloudflare challenge instead of failing Alerts with pending windows and inhibition, so a page always means something
  • Own ids, and every test cleans up after itself Idempotent deploys and throwaway environments, like a fresh kind cluster per CI run
  • Never trust a cached pass against a live system Drift detection: check what's really running, not what state says should be
  • Every quirk explained in the README Runbooks that say why, not just which button to press
